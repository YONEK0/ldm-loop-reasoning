# Qwen3.5-0.8B HybridLoop 下一轮完整训练计划过程 V2

- **计划类型**：下一轮训练与实验全过程计划（过程优化版）
- **项目**：Qwen3.5-0.8B HybridLoop
- **计划状态**：待研究问题与实验臂冻结；未启动训练或 GPU 实验
- **证据来源**：`docs/plans/S08_CAMPAIGN_LOG.md`、`TRAINING_PLAN_V7_0P8B.md`、`COMPUTE_REALIZATION_EXECUTION_CONTRACT_V1.md`，以及 T-2 至 T-11 记录
- **目的**：将下一轮从立项到论文归档组织成完整、可恢复、可审计的训练计划；降低返工、混合检查点、错误成本归因和数据污染风险

---

## 1. 计划目标与边界

本计划规定**下一轮训练的过程和门禁**，不替用户决定新的科学问题或模型配方。它适用于下一轮 0.8B HybridLoop 训练或受控后训练实验；并不表示必须重做此前已完成的 E0–E3、EOS 修复或其他实验。

下一轮的具体研究主张、技能/任务、训练目标、基线和参数预算，须在阶段 0 形成实验注册表后冻结。候选问题可以涉及训练样本效率、可训练参数效率、循环深度质量、退出行为或成本，但一次主实验只选一个主要问题。不得把尚未选定的候选全部塞入一轮训练。

本计划的全程目标是：

1. 在训练开始前定义可证伪的研究问题和公平对照。
2. 先用静态、CPU 和小规模冒烟检查消除配置与脚本错误，再使用正式预算。
3. 训练、模型选择、确认性评测和成本测量分阶段执行，上一阶段未过门禁不自动进入下一阶段。
4. 所有训练状态和逐题评测可恢复；每条结果可追溯至唯一 checkpoint、代码、数据和配置。
5. 对失败、暂停、热节流和异常采取保留现场、分析后再决定的流程，不盲目重试。
6. 最终能够形成论文可用的完整证据链，而非只有一个最终准确率或速度数字。

## 2. 已知基线与启动前需冻结的未知项

### 2.1 已知项目事实

- 基座是 Qwen3.5-0.8B-Base；HybridLoop 现有结构为 E4 + M12 循环 + D8，M 权重共享，最大深度 8。
- 当前 0.8B 具体实现依赖 Qwen3.5 的 GDN/全注意力混合结构、状态语义、层切分、LoRA target 与缓存实现；它还不是跨架构验证过的通用训练配方。
- 历史臂 A/臂 B、Q1 路由器、armB EOS 混合版、armA EOS 版均是不同 checkpoint，不得笼统称为同一个“原模型”或相互替代。
- EOS 1:1 混合方案曾在既有任务/协议下达到 EOS 行为目标并维持质量噪声级；该结果可以作为后续训练的数据格式经验，不自动等于新任务上有效。
- GDN 增量缓存、终止规则、完整任务成本有既有诊断和修复记录；若下一轮改变模型、缓存、解码器或 Transformers 版本，相关正确性门禁须按影响范围重跑。
- 所有既有 checkpoint 只读保留。新实验使用新的 run 目录、实验 ID 和 checkpoint 文件。

### 2.2 每轮启动前必须由实验注册表给出的项目

以下项当前不预填，缺一项不得开正式训练：

- 研究问题、主要假设、可证伪条件、预期结论范围。
- 训练任务/数据来源、生成方法或固定样本清单，以及 train/dev/calibration/confirmation/final-test 划分。
- 实验臂定义：底座哈希、HybridLoop/非循环结构、初始化 checkpoint、可训练参数范围、冻结范围、循环深度/路由策略。
- 各臂训练 token 预算、batch/有效 batch、学习率、优化器、训练步数上限和早停规则。
- 主要终点、次要终点、统计方法、预先接受的质量差/成本差门槛。
- 数据与 checkpoint 是否允许复用；若复用，说明复用对象、来源、训练历史和公平性边界。
- 设备、软件版本、允许的 GPU 预算、预计墙钟和停止条件。

> 若比较参数效率，必须先定义比较的参数量是总模型参数、可训练参数还是训练中实际更新参数；三者不能混用。若比较学习速度，必须记录达到同一质量阈值所用的训练 token、更新步数和卡时。若比较推理成本，必须另行统一 prompt、停止策略、输出长度口径和计时协议。

## 4. P0：研究问题与实验注册

### 4.1 一次只设一个主要问题

在启动前写清：

- **研究问题**：一句话说明要比较什么。
- **估计对象**：差异是由训练架构、训练预算、可训练参数量、退出策略还是系统实现造成。
- **主要假设**：例如“在相同训练 token 下，某臂达到预设技能质量所需可训练参数更少”。
- **可证伪结果**：明确何种结果表示无优势、反方向结果或无法判断。
- **主要终点**：只指定一个主判据；其他作为次要分析。
- **推论边界**：本轮结果针对何种模型、任务、数据、硬件和训练方式，不越界外推。

### 4.2 建立实验臂矩阵

每个臂以唯一 ID 表示，并固定：

| 必填项 | 记录内容 |
|---|---|
| 底座/初始化 | 模型名、checkpoint SHA256、训练历史、tokenizer 版本 |
| 结构 | 原始/循环；E/M/D 划分；循环深度；门控/路由状态 |
| 可训练范围 | 完整模块名、LoRA 秩与 target、冻结模块、训练参数数量 |
| 训练输入 | 数据版本、模板、EOS、packing、截断、loss mask |
| 预算 | 训练 token、更新步、batch/有效 batch、最大卡时 |
| 解码 | greedy/采样、EOS/stop string、最大长度、缓存路径 |

若两臂训练图不同，分别定义各自预算和主要对比意义，不以“配置看起来类似”宣称公平。所有非对称项必须有明确理由和单独解释。

### 4.3 冻结比较与统计方案

- 预先固定配对样本 ID、重复种子、主要指标、置信区间/检验方法、缺失值规则和失败运行处理方式。
- 预先固定早停与选模规则；不得根据确认集或 final test 结果挑 checkpoint、阈值或 prompt。
- 对小样本明确标注 pilot；pilot 不能同时承担无偏最终确认。
- 若训练预算或参数预算两臂不相同，预注册要报告的前沿轴：质量 vs token、质量 vs 可训练参数、质量 vs 卡时或其他定义。

**P0 通过条件**：注册表完整、所有臂和主要终点可复现定义、数据角色互斥、统计方案和最大预算冻结。通过后建立独立实验目录与只读快照。

## 5. P1：数据、代码和评测协议冻结

### 5.1 数据治理

1. 保存原始数据来源、许可/生成方法、样本 ID、内容哈希与构建脚本哈希。
2. 划分 train、训练监控、开发、退出/超参校准、确认和 final test；每个切片声明唯一用途。
3. 生成切片交叉检查报告：重复样本、模板泄漏、相邻生成样本泄漏、与已有训练集/基准集重叠。
4. 统计 tokenizer 后的输入 token、监督 token、EOS token、截断率、packing 跨样本边界数和 loss mask 覆盖。
5. final test 不用于训练、early stop、阈值选择、prompt 选择或实验臂选择。

### 5.2 训练/生成协议预检

- 对代表样本打印 token IDs 和可读 token 序列，核对题目、推理/技能答案、结束标记、EOS ID、标签移位与 mask。
- 对生成路径明确区分自然 EOS、stop string、答案格式边界、max token 截断；逐题分开存储。
- 检查训练样例拼接是否让模型学会跨样本续写；确认 EOS 和分隔符在训练目标中确实受到监督。
- 对固定解码实现，验证 prefill 产生的首个 token 是否重复喂入、位置 ID 是否绝对递增、batch 中结束样本处理是否正确。

### 5.3 代码与运行配置冻结

保存：git commit（若非 git 则保存完整文件清单及 SHA256）、Python 环境、CUDA/驱动、PyTorch、Transformers、模型 config、参数统计、启动命令与环境变量。任何正式变更都建立新的 revision，旧结果不覆盖。

**P1 通过条件**：数据清单、token 检查、EOS/停止协议、loss 目标和代码哈希均可复核；验证/测试用途已经写入注册表。

## 6. P2：静态检查、CPU 预检与恢复演练

GPU 授权前完成：

1. **语法与导入**：所有正式脚本通过语法、导入、参数解析检查；启动模块有 main guard；无意外导入即训练。
2. **单 batch 结构检查**：shape、dtype、attention mask、位置编码、标签移位、loss mask 和预期可训练参数梯度范围正确。
3. **优化器/训练恢复单元测试**：保存后重新加载模型、优化器、scheduler、AMP scaler、随机状态、step、数据游标；比较恢复前后下一 batch 的 sample ID、loss 与参数更新一致性。
4. **逐题记录测试**：模拟中断和重启，验证完成题跳过、缺失题补跑、重复运行保留 attempt ID，聚合由 sidecar 重建。
5. **指标脚本测试**：以人造 JSONL 检查 strict、完成率、EOS、stop string、max_new、置信区间、计算账口径；测试千分位、负数、小数、解析失败等答案格式。
6. **面板测试**：开板、刷新、进程重启后从日志恢复状态；确认面板不持有唯一数据副本。
7. **检查点容量与原子性**：临时文件写完再原子替换；检查磁盘余量和文件哈希。

**P2 通过条件**：恢复演练和聚合测试通过；GPU 正式工作不再依赖手工改 JSON 或从不完整 history 推测结果。

---

## 7. P3：GPU 冒烟与资源标定（独立授权）

### 7.1 启动前

- 记录实际 GPU 型号、总/可用显存、温度、功耗、时钟、利用率、外部进程和系统供电状态。
- 核对当前时间、目标截止时间、用户授权预算和可以接受的暂停点。
- 确认面板可访问，训练日志路径和容量正常。

### 7.2 冒烟顺序

1. 单前向与单反向；检查 loss 有限、梯度非零且仅落在注册参数。
2. 5–10 步训练；测显存峰值、稳态 step time、吞吐、温度和功耗趋势。
3. 两臂各做对称冒烟；若训练图/模块不同，分别量化吞吐，不能用较快臂估较慢臂。
4. 端到端生成烟测：自然 EOS、stop string、hit max_new、答案格式和终止日志都覆盖到。
5. 实际暂停并恢复一次，确认不丢 step、optimizer 或数据顺序。

### 7.3 资源估算

总时间分解为：环境/加载、正式训练、定期验证、行为探针、确认评测、墙钟重复、归档。每一项用同模型/同训练图/同 batch 的实测速度估算，并附保守余量。GPU 持续热节流、步速偏离标定范围、显存接近上限或有外部任务时，暂停并重新评估，而不是边跑边扩大预算。

**P3 通过条件**：资源预算合理、进程无外部负载污染、检查点恢复成功、数据路径和终止行为符合注册表。

## 8. P4：正式训练执行

### 8.1 开跑前冻结

- 复制 P0 注册表、数据清单和代码哈希到 run 目录。
- 保存训练开始前 checkpoint 的永久只读副本和 SHA256。
- 确认训练目标、计划步数/token、batch、学习率、优化器、warm-up/decay、梯度裁剪、精度、梯度累积、loss 权重和随机种子。
- 确认周期存档频率、评测频率、转折点指标、early stop 规则和人工暂停语义。

### 8.2 实时记录

每步或每固定窗口记录：step、epoch/数据游标、有效训练 token、各 loss 分量、学习率、梯度范数、参数更新范数、step time、tokens/s、峰值显存、GPU 温度/功耗；循环模型另记各深度路由/退出统计。训练逐步日志 append-only。

### 8.3 周期和永久 checkpoint

周期 checkpoint（建议频率由 P3 速度与中断成本决定）包含：模型、优化器、scheduler、AMP/scaler、Python/NumPy/CPU/CUDA 随机状态、全局 step、epoch、数据 permutation/游标、有效 token 数、配置和代码/数据哈希。

永久 checkpoint 由预注册转折点触发，例如：验证质量首次达到阶段门、路由分布发生稳定转变、训练平台或最佳开发点。永久档与周期档分开命名，附触发指标、对应验证结果和 checkpoint hash。训练完成/提前停止时保存终档。

### 8.4 暂停与异常流程

遇到 NaN/Inf、异常 loss 跳变、梯度归零或爆炸、乱码/复读、EOS 行为异常、OOM、外部 GPU 负载污染、热节流、检查点写入失败或实现与注册表不符：

1. 停止当前进程；确认 GPU 释放。
2. 保存最近 checkpoint、日志、stderr/stdout、GPU 状态、未完成 sidecar 和代码状态。
3. 写问题摘要：现象、最后有效 step、受影响样本/指标、可能根因、已排除项、所需信息。
4. 不删除失败产物、不回滚用户文件、不静默修改配方。
5. 提出修复分支、资源需求和预期判读；修复/新实验等待明确授权。

**P4 结束条件**：达到预注册预算、early stop 或停止门；报告触发原因和实际总 token/卡时。不得因效果暂时不佳而自动延长或换配置。

## 9. P5：开发验证、选模和早停

### 9.1 训练监控评估

按预注册频率在训练监控集运行，不做最终能力声明。记录开发质量、loss、EOS/停止行为、深度分布和生成异常趋势。所有评估都绑定 checkpoint SHA/step。

### 9.2 模型选择

只用开发集按预先定义的单一规则选择 checkpoint。不得先看多指标再挑最有利的一个；若需多目标排序，须在 P0 预先定义优先级或 Pareto 判读方法。若模型被选中后还进行继续训练，该后续阶段视为新实验/新 checkpoint lineage。

### 9.3 退出与停止策略

阈值只在 calibration slice 选择；之后冻结。短 pilot 仅判断实验是否健康，不作为最终通过。报告自然 EOS、工程 stop、格式完成与 max_new 截断分别计数。

**P5 通过条件**：候选 checkpoint 按注册规则选定；没有使用确认集或 test 作选择；确认阶段的配置、权重和阈值均被冻结。

## 10. P6：独立确认与质量门

在 confirmation slice 上按冻结配置做确认评测；若实验臂配对，固定题目 ID 和相同 prompt/解码协议。输出逐题结果、点估计、配对差、bootstrap/置信区间、失败样本与解析错误。

按研究问题启用对应验收：

- **学习效率**：达到预设质量线所用训练 token/更新步/卡时，报告学习曲线而非只比终点。
- **参数效率**：分别报告总参数和可训练参数；画质量–参数曲线；比较达到相同预注册质量线的最小参数预算。若任务饱和或无难度前沿，结论必须是“本任务未辨识差异”。
- **质量保持退出**：固定深度和 adaptive 做配对质量对比，同时报告退出深度分布；平均深度下降本身不算通过。
- **EOS/终止行为**：报告 EOS 命中、EOS 位置、过早停止、stop rule、hit max_new、答案质量；不能把工程停止称作自然 EOS。
- **推理成本**：同质量协议下分别报告每 token 工作量、输出长度、整题成本，不把单 token 降价当成整题省算力。

若确认集结果触发修改，不得继续把同一确认集称为独立确认；修改后需要新的确认数据或将其降级为开发数据并如实说明。

## 11. P7：推理正确性、性能和完整任务账

只有研究问题需要推理/成本结论时启动本阶段。新训练权重、缓存、tokenizer、解码器或软件版本改变后，重新做影响范围内的正确性门禁。

### 11.1 正确性

- 检查单遍/循环参考 logits、teacher-forced cache 对齐、绝对位置、GDN conv/recurrent state、全注意力 KV、cache reset 与多步 decode。
- token 级跳过若被纳入本轮，训练与部署必须采用同一缺失状态/缓存语义；推理侧单独删除 token 不视为有效方法。
- 先在小样本全精度参考中区分逻辑错误和 dtype/运算次序误差；数值容差在正式计时前冻结。

### 11.2 计数与计时

分别记录：

- 物理 decoder layer calls、M layer calls、缓存回填/状态更新额外计算。
- FLOPs（若有可信 profiler/公式）与估算方法；层调用只能标为代理量。
- prefill/TTFT、decode ms/token、整题墙钟、tokens/s、输出长度、峰值显存。
- warm-up、重复数、mean/median/p50/p95、GPU 外部负载状态、硬件/软件版本。

### 11.3 完整任务成本

按逐题计算成本并做配对汇总。至少拆成：模型每 token 成本 × 实际生成步数 + prefill/探针/路由/缓存补算/工程 stop 等固定成本。训练本身的额外预算若属于研究主张，也单列 amortization 情景，不混入单次推理成本。

**P7 通过条件**：正确性门通过；计时协议合格；成本结论与质量结论同表报告；无法分离训练收益、循环计算收益、kernel 收益时不得做单因归因。

### 12.1 结果冻结包

- 最终永久 checkpoint、对应日志和指标触发依据。

### 12.2 论文表述分账

正文或附录分开写：

1. 训练方法对质量/学习曲线的影响。
2. 循环/路由机制对深度分布和执行计算的影响。
3. 缓存、GDN kernel、编译/量化等系统工程优化的影响。
4. EOS 和工程停止对生成长度及整题成本的影响。
5. 总参数、可训练参数、训练 token/卡时与推理成本。

每个百分比写明参照系、分母、数据切片、硬件、计时口径和质量差异。不能把 E3 的 kernel 提速、EOS 产生的长度缩短、循环深度节省相乘后直接当成已实测总收益。
