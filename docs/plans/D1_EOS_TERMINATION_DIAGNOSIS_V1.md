# D1 · 生成不终止（无 EOS）问题诊断报告 V1

- **日期**：2026-10-20
- **性质**：只读诊断（未改任何代码、未跑任何 GPU；全部结论来自代码审计 + 既有实测数据）
- **用途**：供协作 AI 对齐。回答"为什么生成 token 数没有减少、整体计算成本仍高于单遍模型"，并给出待授权的最小验证实验设计。
- **证据等级约定**：【实测】= 有 hook/日志/JSON 数据；【代码确认】= 直接读码可验证；【推断】= 证据链强但未直接测量；【未确认】= 需实验。

## 0. 摘要

**模型不吐 EOS 不是 bug，而是训练数据从未示范过 EOS + Base 底座的必然结果。**
停止逻辑、EOS token 身份、kernel 路径全部排查无恙（假设 B/C/D 全部排除）。
根因定位在数据格式层：S08 训练流把 GSM8K 样例用 `\n\n` 无缝拼接、全程无 EOS
（`s08_arch.py:258-264`），推理 prompt 又是零样本 `'Q: …\nA:'`（`s42_e2_benchmark.py:367`），
模型学到的条件分布是"`#### N\n\n` 之后续写下一题 `Q:`"，而非终止。
后果：4 模式 × 40 题、约 32,000 个 decode 步中 EOS 一次都没赢过 argmax，
每题都跑满 200 token 截断——每 token 省下的层调用（36.6 vs d8 的 108）
无法在步数轴上兑现，全任务账对 armA 单遍净亏 ~53%。
修好 EOS（推理侧演示或训练侧补 EOS）是全任务算力账翻正的前置条件；
打平线在 d*≈2.05 下为 **128–131 token**（口径见 §4）。

## 2. 问题一：为什么生成没有提前结束

### 2.1 逐项排查结果

| 检查项 | 结论 | 证据 |
|---|---|---|
| `eos_token_id` 身份一致性 | **一致，假设 B 排除**【实测】 | `s08_arch.py:30` 的 248044 与 tokenizer 实测 `eos_token_id=248044` 相同；`<|im_end|>`=248046 未误用 |
| generation_config | 不参与【代码确认】 | 快照为 Base 模型、无 generation_config.json；推理不用 HF `generate()`，自定义循环直接比 EOS_ID |
| `min_new_tokens`/`forced_eos`/`stop_strings`/采样 | 均不存在【代码确认】 | `s42:189-244 generate_item`：贪心 argmax，无 logits processor；`--max-new` 默认 200（:279）是唯一上限 |
| batch 内序列互相拖累 | 不存在【代码确认】 | batch=1 逐题生成（单条 p_ids） |
| 自定义 kernel 吞停止信号 | 不存在【代码确认+实测】 | GDN kernel 只算状态不碰 token 选择；E1 已证增量 vs 全重算 0 语义翻转 |
| EOS 生成了但未识别 | 未发生【实测】 | 唯一提前出口是 EOS（:220）；160 条全部恰好 200 ⇒ 32,000 步里 EOS 从未进 argmax 首位。若识别失效应出现 gen_tokens<200 且 eos=False，无此现象 |
| 200 是自然长度还是截断 | **截断**【实测】 | "finished" 36-37/40 是评分器格式判定（`scorer_strict.py:103 gsm8k_finished`：EOS 或 `#### N` 后接自然边界/行首 `Q:`），非生成终止 |

### 2.2 根因【代码确认 + 推断】

- **训练流无 EOS**【代码确认】：`s08_arch.py:258-264 build_blocks_from_jsonl` 用
  `''.join(fmt_gsm(r))` 拼接，`fmt_gsm`（:253-255）以 `#### {answer}\n\n` 结尾，样例间仅
  `\n\n`，全程无 EOS token；全项目 grep 确认训练侧零 EOS 使用。
- **推理 prompt 零样本**【代码确认】：`s42:367` `'Q: ' + question + '\nA:'`，无 EOS 演示。
- **行为推断**【推断，强】：微调后条件分布 = "`#### N\n\n` → 续写下一题 `Q:`"；
  评分器 v1.1 修正规则（接受"后接行首 `Q:`"）即为该现象的文档学证据。
- **对照证据**【实测】：同 harness 家族的 Qwen3-4B-Thinking（指令模型）在 1024 预算下
  mean 784.7 token（大量自然 EOS）⇒ 不吐 EOS 是训练谱系属性，非测试装置属性。

## 3. 问题二：循环退出为什么不减少 token 数

**两机制独立，结构与实证双重确认。**

- 结构【代码确认】：终止条件只在 `generate_item`（EOS 或 max_new，:220）；深度 d* 只进
  `fixed_depth_forward` 的圈数上界（:138）。门控/router/l1gate 无任何通向 lm_head 或
  终止判断的路径；门控训练目标（Q1 生存概率）是"预测质量需要几圈"，与"回答该不该结束"
  是两个目标。
- 实证【实测】：EOS 缺席对深度不变——d=1（armA）/2/8/adaptive 四种深度全部 200 无 EOS。
  "循环模型跑到上限但每 token 已提前退出循环"就是当前实测状态。
- 保留项【未确认】：深度会轻微改变每步 logits（d8−d2 有 2/40 tie 级翻转），原则上可能
  微调 EOS 概率，但无机制训练此事，且 EOS 从未进 argmax 首位 ⇒ 无观察效应（待 T-4 量化）。

## 4. 问题三：131 token 打平线复核

| 口径 | armA 单遍 | seq_adaptive | 比值 |
|---|---|---|---|
| 每 token decode 层调用 | 24.0 | 36.6 | 1.525 |
| 每题固定开销（层调用） | prefill 24 | prefill 36.6 + 探针 100 | — |
| 全题层调用（200 token） | 4,824 | 7,452.6 | 1.545 |
| decode 墙钟 ms/token（E3 后） | 65.7 | 100.6 | 1.531 |
| whole 墙钟（含 TTFT） | 13.44 s | 20.64 s | 1.536 |

- **decode-only**：L ≤ 24/36.6 × 200 ≈ **131**（原估算正确）。
- **计入 prefill+探针**：L ≤ (24×200+24−136.6)/36.6 ≈ **128**。一般式
  L ≈ 0.656×L_armA − 3；d*=3 时系数 24/48=0.50。**131 非普适常数**，是
  "d*≈2.05、armA 同在 200 截断"条件下的值。
- **层调用 ≠ FLOPs 界定**：层调用是代理——armA 24 层 = 18 GDN + 6 全注意力，多出的
  12.6 层 ≈ 9.5 GDN + 3.2 attn（M 每圈 9 GDN + 3 attn）。本机 batch=1 贪心下代理成立
  （墙钟比 1.531 vs 调用比 1.525，偏差 0.4%）；换批量/硬件/长序列需重标定。
- **2.65–3.19× 的基线核实**：这是**同模式内 kernel 替换 A/B**（decode GDN 步
  chunk→官方 recurrent；armA 2.90×/d2 2.76×/adaptive 2.65×/d8 3.19×），同协议同题；
  不是循环结构节省，不得混入"省算力"叙事。d8 n=15（偏离已在阶段日志注明）。

## 5. 已确认 / 未确认清单

**已确认**：EOS 身份一致（B 排除）；停止逻辑正确、batch=1、无 min/forced/stop（C 排除）；
200=截断非自然长度（D 排除）；32,000 步 EOS 从未赢 argmax；训练流无 EOS；prompt 零样本；
finished 是格式判定；EOS 缺席对深度 {1,2,8,adaptive} 不变；打平线 128–131 双口径；
2.65–3.19× 为 kernel A/B 口径。

**未确认**（需实验）：
1. EOS 在 top-K 的实际排名（"想停但贪心不选" vs "概率≈0"）→ T-2；
2. EOS 演示能否推理侧直接修复、自然长度分布是什么 → T-3；
3. 深度是否影响 EOS 分布 → T-4；
4. 遗留异常：fixed_d2 峰值显存 ~3,048MB 高于 d8 ~1,622MB，未解释（与成本账无关，待复核）；
5. 侧车不存生成文本与 eos 字段——连续编题行为目前靠评分器规则间接佐证。

## 6. 最小验证实验（不改权重；T-0/T-1 已由本次排查完成）

### T-2 logits 审计（~1 卡·分钟，10 题）
复用 `generate_item`，仅加记录：每步 top-5 (id, prob)，重点存首个 `####` 后 3 步。
- EOS 进 top-1 → 与 gen_tokens=200 矛盾 ⇒ C 复活（预期不会发生）；
- EOS 稳定 rank 2-3 → "想停但贪心不选"，推理侧 logit-bias/采样可立即修复；
- EOS 全程不在 top-5、`Q:` 居首 → 根因（格式）完全坐实。

### T-3 EOS 演示消融（~2 卡·分钟，同 10 题 × 3 prompt）
(i) 现零样本；(ii) few-shot 且样例间插 EOS；(iii) few-shot 无 EOS（=训练格式）。
- (ii) 首 EOS ≤150 token → 根因=未演示，且直接得到自然长度分布（成本账关键输入）；
- (iii) 仍 200 → 训练格式主导，推理侧修复无效，必须训练侧修。

### T-4 深度×EOS 交叉（~1 卡·分钟，可选）
prompt (ii) × 深度 {1,2,8}。EOS 位置分布不随深度移动 → 两机制独立的量化版；
移动 → 自适应深度设计需把 EOS 纳入考虑。

## 7. 修复优先级

1. **推理侧（零训练，先做）**：T-3 成立则协议升 v1.2 = few-shot+EOS 分隔（或 EOS
   logit-bias / `#### N` 边界 stop-string）。**协议变更须整体重跑质量矩阵**，且标注为
   工程止损，非模型能力提升。
2. **训练侧（真正修复，与内化讨论合流）**：训练流每样例末尾接 EOS（`fmt_gsm` 一行改动
   量级 + 重建块）。直接决定 T-partial（≤131/128 打平线）能否达标——无 EOS 则任何深度
   优化都兑现不了全任务节省。
3. **token 级动态退出（E4-A）**：与 EOS 正交，省每 token 单价；EOS 修好后两者相乘才是
   完整账。
4. **不必再动**：kernel（E3 已修）、精确缓存（E1 已证）。
