## 0. 直接回答："能否给出一个符合循环深度、且参数效率不低于 CoT 平均水准的训练方案？"

**目前不能给出一个"已验证可用"的方案。** 下面的方案是**在现有全部证据下最合理的候选**，
但它有一个已知未解的核心问题（hop 间竞争），必须先解决或绕开才能产出成品模型。

诚实陈述：
- **机制层面**：循环承重成立（H-001/H-002/H-003 均已证伪对立面，属可复现的正面结论）
- **训练层面**：稳定性未解决——6 个配置无一能让 5 个难度级同时达标
- **参数效率对比 CoT**：这个对比**还没有条件做**，因为我们的模型本身还没训稳

## 3. 核心未解问题（成品模型的唯一拦路虎）

**症状**：任一时刻，相邻 hop 呈严格互斥。服务器基线实测完整轨迹：

```
step  6000:  hop2=0.035  hop3=0.98          ← hop2 归零
step 18000:  hop3=0.015  hop5=0.955         ← hop3 归零
step 20000:  hop3=0.0    hop6=0.895         ← hop3 归零，hop6 上来
step 22000:  hop2=0.995  hop3=0.46          ← hop2 回来，hop3 半崩
```

关键观察：**train loss 全程正常（0.0–0.26），但 eval 精度剧烈震荡**。
说明模型对训练分布拟合良好，但不同难度在做零和竞争。

**已确认不是**：容量（H-008）、读出层共享（H-009 只解释一部分）、
课程顺序（H-010）、优化器/正则（H-004/005/006）。

**最可能的机制**：共享 core 在同一个状态上，第 k−1 轮要输出 hop_k 的答案，
第 k 轮要输出 hop_{k+1} 的答案。两者目标表示几乎相同但答案不同，形成直接冲突。

## 4. 候选方案（按可行性排序，均未验证）

### 方案 A：轮次索引显式监督（推荐首选）
**做法**：在共享 core 中加入显式的"当前轮次"条件信号（如 learned round embedding
已存在，但改为更强的 FiLM 调制或 additive bias），并**对每一轮的输出施加监督**，
使第 t 轮明确只负责 hop_{t+1}。

**为什么可能有效**：H-009 证明"解耦读出"有帮助（+0.089），说明冲突部分来自
"同一套参数要服务不同轮次"。显式索引让模型能条件化，而不需要隐式分离。

**参数代价**：极小（round_emb 已存在，FiLM 约 +2K）

**风险**：如果 round_emb 已不足以解决（当前已在用），强化版本可能仍不够。

### 方案 B：解耦 core 状态（彻底但损害参数效率）
**做法**：每轮使用独立的 state 投影矩阵（W_down/W_up per round），共享 attention/FFN。

**代价**：参数 +8×（每轮一套投影），**直接损害 H-003 的参数效率主张**

**适用场景**：如果论文重点从"参数效率"转向"机制可行性"，这是最可能成功的做法。

### 方案 C：改写任务，避免轮次冲突
**做法**：不让不同 hop 共享同一输出映射——例如每个难度用不同的输出 token
（hop2→答案A、hop3→答案B 的格式），或改成"输出剩余步数 + 答案"的双头结构。

**优点**：从任务设计上消除冲突，而非硬扛
**风险**：改变任务后，与已有对角线结论的可比性下降

### 方案 D：接受震荡，用快照集成
**做法**：承认无法同时保持全部 hop，改为在训练中持续保存"每个 hop 都还不错的
时刻"，最后做权重平均或多快照集成。

**优点**：工程上可行，不需要新机制
**缺点**：不解决本质问题，集成成本高，且"每个 hop 都不错"的时刻可能不存在

## 5. 参数效率对比 CoT 的方法（待条件成熟后执行）

用户要求"参数效率至少不能低于其他论文相较 CoT 模型提升的平均水准"。
这个对比需要三个量，目前只有第一个可用：

| 量 | 状态 |
|---|---|
| 我们的模型在同等参数下的能力 | 可测（但对角线不稳定） |
| CoT 基线在同等参数下的能力 | **未测**——需要同架构 dense + 文本 CoT 基线 |
| 其他论文的"提升幅度"基准 | 需文献核实具体数字（pp-hop 预算、Saunshi 等的报告值） |

**必须先解决 §3 的竞争问题，这个对比才有意义**——否则比较的是一个训不稳的模型。

## 6. 建议的执行顺序（服务器剩余时间内）

1. **方案 A**（轮次索引显式监督）：改动小、不损参数效率，2 小时内可验证
2. 若 A 无效 → **方案 B**（解耦 core 状态），接受参数效率损失，用来确认机制上限
3. 若 B 成功 → 明确论文结论是"机制可行，但需牺牲参数效率"
4. 若 B 也失败 → 转方案 C（改任务），或接受"1.4M 规模下存在不可绕过的寻址冲突"作为结论
