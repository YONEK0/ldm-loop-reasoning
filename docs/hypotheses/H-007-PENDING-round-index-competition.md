# H-007 [待验证] 相邻 hop 的轮次索引竞争（根因假说）

**假说**：模型用同一个共享 core + 同一个读出层，要在第 k−1 轮输出 hop_k 的答案。
hop_k 与 hop_{k+1} 只差一轮，读出的目标表示几乎相同但答案不同 → 模型在两者间
来回横跳，学会一个就毁掉另一个。这是**架构层面的容量/寻址冲突**，不是优化问题。

**支持证据（强，但均为观察性）**：

三个种子、四种配置反复出现"相邻 hop 严格互斥"：

| run | 步数 | 现象 |
|---|---|---|
| seed17+EMA | 22k | **hop5=0.00 同时 hop6=1.00** |
| seed31+EMA | 8k | **hop2=0.005 同时 hop3=0.985** |
| seed53（无EMA） | 20k | hop4=0.01、hop5=0.99 |
| seed53+EMA | 20k | hop4=0.01、hop5=0.99、hop6=0.02 |

不是"全面遗忘"（那会所有 hop 一起掉），而是**成建制的交替崩溃**。

**与已有观察的一致性**：
- 解释了 E-002（seed 方差）：不同种子只是停在不同震荡相位
- 解释了 E-006（hop8 外推失败）：观测到"hop_k 答案出现在第 k−1 轮"的偏移，
  实为跷跷板在相邻轮次间跳
- 解释了为什么 lr/EMA/加步数都只能有限缓解：它们改变震荡幅度，不改变竞争本身

**判别实验结果（2026-10-26，服务器 2080Ti）**：

| 改造 | 峰值 r8 | vs 基线 0.671 | 跷跷板是否消失 |
|---|---|---|---|
| H-008 加宽 d=384（3.9×参数） | 0.669 | **−0.002（零收益）** | **否，反而更剧烈** |
| H-009 per-hop 读出头 | 0.760 | **+0.089** | 部分缓解，未消失 |

**当前判读（更新）**：本假说的**"容量不足"分支已被 H-008 证伪**；
**"读出层共享"分支被 H-009 部分支持**（hop4 从 0.815→0.90，峰值 +0.089），
但不足以根治——hop5/6 仍在 0.53–0.61，跷跷板仍周期性出现。

**修正后的假说表述**：竞争主要发生在**共享 core 的轮间状态更新路径**，
而非读出层；读出层只是一个次要的耦合点。

**下一步候选**：
1. 解耦 core 状态（每轮独立 state 投影）——但损害参数效率（H-003）
2. 轮次索引显式监督（强约束第 t 轮只服务特定 hop）——不增参数
3. 重新审视任务设计：可能是任务本身要求"同一网络在不同轮次输出不同映射"，
   这在共享权重下本质困难

**判定标准（维持）**：
- 证实：任一架构改造使 3 个种子都能同时保持全部 hop ≥0.95
- 证伪：所有候选改造全部失败
